# 대시보드 요청 — 테이크 묶음 표시 + 클립별 공개 예약

> 2026-08-06 합의. **머신 쪽 변경은 끝났고**(아래 §1), 대시보드에서 해줘야 하는 것만 정리한 문서다.
> 현재 동작: 한 번의 분석이 쇼츠를 최대 3편 내고, 겹치지 않는 것은 **전부 검수함에 올라간다.**

---

## 0. 왜 바뀌었나

예전에는 실행 1회 = 쇼츠 1편이었다. 그 1편이 반려되면 다음 실행이 **전 과정을 다시** 돌렸다
(분석이 편당 30~90분의 대부분을 차지한다 — 2026-08-05 리와인드포차는 겹침 재생성으로 3시간).

이제 `--max-shorts 3` 으로 **분석 1회에 테이크 3개**를 만든다. 렌더만 3배이고 분석은 1회다.
셋 다 검수함에 올라가므로, 사람이 보고 **쓸 것을 고르고 각각 다른 날짜로 예약**할 수 있다.

---

## 1. 머신 쪽에서 이미 하는 것 (대시보드가 전제해도 되는 것)

| 무엇 | 결과 |
|---|---|
| 테이크 생성 | 한 job 에 `shorts.mp4`·`shorts_2.mp4`·`shorts_3.mp4` + 각각의 `edit_plan[_n].json` |
| 중복 제거 | 기존 장면·앞 테이크와 겹치는 테이크는 **올리기 전에** 버린다(같은 대목 3연발 방지) |
| DB 적재 | 테이크마다 **별개 clip row**. 같은 `clip_metadata.ai_video_run_id`, 다른 `clips.episode`(= `shorts_1`/`shorts_2`/`shorts_3`) |
| 검수 사본 | 테이크마다 `review-clips/<machine>/<clip_id>.mp4` 로 업로드 + judge 기록 |
| 발행 | 승인된 클립의 **그 테이크 파일**을 올린다(`clips.episode` 로 어느 mp4 인지 판별) |

★ **묶음 키는 이미 있다: `clip_metadata.ai_video_run_id`.** 같은 값이면 같은 분석에서 나온
형제 테이크다. 스키마 변경 없이 그룹핑이 된다.

---

## 2. 요청 1 — 검수함에서 형제 테이크를 한 묶음으로 보이게

**문제**: 지금은 세 클립이 서로 무관한 항목으로 나열된다. 검수자가 "이건 아까 그거랑 같은
작업에서 나온 다른 버전"임을 알 수 없어, 중복처럼 보이거나 셋 다 반려하게 된다.

**요청**:
- `ai_video_run_id` 가 같은 클립을 **한 카드(또는 한 행 그룹)** 로 묶어 보여줄 것
- 묶음 안에서 테이크 번호(`clips.episode` = `shorts_1|2|3`)를 **테이크 1/2/3** 으로 표기
- 묶음 헤더에 공통 정보(채널·작품·회차 `clips.source_episode`)를 한 번만
- 각 테이크는 **개별로 승인/반려**할 수 있어야 한다(묶음 단위 일괄 처리는 선택)

**있으면 좋은 것**: 테이크별 구간(`clips.origin_start_sec`~`origin_end_sec`)을 함께 보여주면
"같은 대목인지 다른 대목인지"를 재생 전에 판단할 수 있다.

---

## 3. 요청 2 — 승인 시 공개 날짜·시각을 고르게

**문제**: 지금은 발행 루프가 `config/loop_policy.json` 의 `publish_times`(예 `["19:00"]`)에서
**가장 이른 빈 슬롯**을 자동으로 잡는다. 셋을 다 쓰고 싶어도 날짜를 사람이 정할 수 없다.

**요청**:
- 승인 UI 에 **날짜 + 시각 선택**(선택 사항, 비우면 지금처럼 자동 슬롯)
- 저장 위치: `review_decisions` 에 컬럼 하나 — `scheduled_publish_at timestamptz NULL`
  (마이그레이션은 대시보드 쪽에서 `docs/migrations/00NN_*.sql` 규약으로 추가)
- 의미: "이 클립을 이 시각에 **공개**되도록" — 업로드는 그 전에 미리 이뤄지고, 유튜브
  네이티브 예약(`publishAt`)으로 그 시각에 공개된다
- 검증: **과거 시각 금지**, 같은 채널에 같은 시각 두 건 금지(발행 루프가 슬롯 충돌을 못 푼다)

**머신 쪽 대응**(대시보드가 값을 넣어주면 이쪽에서 붙인다): `scene_publish_loop` 가 승인 클립의
`scheduled_publish_at` 이 있으면 그 값을, 없으면 기존 자동 슬롯을 쓴다. 이 연결은 컬럼이
생긴 뒤 한 줄 수준이라 대시보드 작업이 먼저다.

---

## 4. 요청 3 — 폐기(반려) 표시는 지금 그대로면 충분

`review_decisions.decision='rejected'` + `reject_type`(`scene`|`production`) 이면 머신 쪽이
알아서 처리한다: 반려분은 회차 카운트에서 빠지고, `reject_type='scene'` 은 그 구간을 다시
만들지 않도록 회피 목록에 남는다(`production` 은 같은 장면 재시도를 허용).

다만 **묶음 전체를 한 번에 반려**하는 버튼이 있으면 편하다(테이크 3개가 다 별로인 경우).

---

## 5. 확인 방법 (대시보드 작업 후)

```sql
-- 형제 테이크가 묶이는지: 한 run_id 에 여러 라벨
select m.ai_video_run_id, c.episode, c.id, c.origin_start_sec, c.origin_end_sec, c.storage_path
from clips c join clip_metadata m on m.clip_id = c.id
where c.storage_path like 'review-clips/%' order by m.ai_video_run_id, c.episode;
```

예약이 붙은 뒤에는 `review_decisions.scheduled_publish_at` 이 채워지고, 발행 루프 로그의
`[예약 현황]` 줄에 그 시각이 그대로 찍혀야 한다.
